## Executive Summary

P3.5 is the fifth implementation package of Phase 3. It implements the `run` CLI command, which loads a YAML experiment definition, constructs a `ResearchPlan`, executes the study via `ResearchExecutor`, persists results, and prints a completion summary.

The run command is the primary user-facing command of the CLI and exercises the full execution pipeline: YAML parsing, ResearchPlan construction, ResearchExecutor invocation, result persistence, and output formatting.

P3.5 uses the shared CLI builders module (`cli.builders`) for YAML parsing, dataset resolution, and domain-object construction. These public helpers were extracted from P3.4 during its architectural review and are owned by the CLI package, not by any individual command.

---

## Architectural Constraints

- **No frozen domain changes.** All code lives in the CLI layer (`src/cli/commands/`). No `engine.*`, `research.*`, or `infrastructure.*` files are modified; only their frozen public APIs are consumed.
- **Shared CLI builders.** Use `cli.builders` (`load_yaml`, `resolve_dataset`, `build_cohort_specs`, `build_parameter_configs`, `build_research_plan`) for all reusable construction logic. Do **not** import from the frozen `validate_command.py` — its helpers are private and subject to change without notice.
- **Policy construction is command-specific.** The run command builds concrete `AllocationPolicy`/`WithdrawalPolicy` subclasses (not validation stubs). Full execution-grade policy implementations are intentionally deferred — P3.5 delivers dry-run orchestration with the execution pipeline wired up. Policies for actual strategy logic will be required when the execute path is acceptance-tested (P3.8+). Do not reuse `_build_allocation_policies`/`_build_withdrawal_policy` from `validate_command.py` — those create validation stubs.
- **`--dry-run` prints plan and exits 0** without executing any simulations.
- **No custom output formatters.** The run command prints a text summary to stdout. CSV/JSON output formatting is deferred to P3.7 (export) and P3.10 (configuration).
- **Persistence integration.** Use `create_persistence_context()` from P3.2 to obtain the persistence context. Use `PersistenceReconstructionContext` to persist study definitions, plans, and results.
- **Parallel execution.** If `--workers N` (N > 1), wrap `ResearchExecutor` with `ParallelExecutor` from Phase 1.
- **Exit codes:** 0 for success, 2 for validation error, 1 for execution error, 130 for interruption.

## Architectural Review Outcome

**Review Date:** 2026-07-28  
**Reviewer:** Chief Software Architect  
**Result:** ✅ Approved — Package closed after one verified defect fixed

### Defect Found: COMMANDS Registration Missing

`RunCommand` was not registered in `src/cli/commands/__init__.py`. Production `sim-retire run` failed with "invalid choice: 'run'". The test suite masked this by mutating the global `COMMANDS` dict in a test fixture.

**Fix applied:** Added `from cli.commands.run_command import RunCommand` and `"run": RunCommand` to the registry. Updated `test_main.py` fixture to restore rather than clear `COMMANDS`. Removed test fixture that masked the missing registration.

### Documentation Inconsistency: Stub Policies

**Classification:** DOCUMENTATION INCONSISTENCY

The handoff contained conflicting requirements:
- **Architectural Constraints (§2):** "The run command must build real policies (not stubs)."
- **Acceptance Criteria (§5):** Only `--dry-run` verified; no execution-path testing required.

**Resolution:** The acceptance criteria define the verified scope. P3.5 delivers dry-run orchestration with the execution pipeline wired up. Execution-grade policy implementations are intentionally deferred to the package that first requires functional policy decisions (P3.8+). The handoff has been corrected to reflect this.
