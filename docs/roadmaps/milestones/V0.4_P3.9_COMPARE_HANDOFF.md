## Executive Summary

P3.9 implements the `compare` CLI command, which compares multiple allocation strategies using the frozen v0.3 `StrategyComparator` to produce a deterministic ranking of strategies by success rate and other metrics.

The compare command is the last strategy-level CLI command before P3.10 (Configuration & Handoff). It exercises:

- The frozen v0.3 **StrategyComparator** — pure analytical consumer for deterministic comparative analysis
- **Multi-strategy execution** — runs N separate full studies (one per strategy) and aggregates results for comparison
- The shared `cli.policies` module — reuses the concrete policy implementations from P3.8
- The existing execution and persistence pipeline — each strategy's results are persisted individually

This package is the **seventh concrete CLI command** and the **ninth Phase 3 package**. It closes the CLI command set: `validate`, `run`, `list`, `export`, `optimize`, `compare`.

## Architectural Constraints

- **No frozen domain changes.** All code lives in the CLI layer (`src/cli/commands/`). No `engine.*`, `research.*`, or `research.optimization.*` files are modified — only their frozen public APIs are consumed.

- **StrategyComparator is frozen.** The `StrategyComparator` class at `src/engine/domain/optimizer/strategy_comparator.py` is v0.3 frozen. Its `compare()`, `EvaluationResult`, `RankingRule`, `StrategyComparisonReport`, `GroupingDimension` types must be consumed as-is. No modifications.

- **No frozen command changes.** Do not modify `validate_command.py` (P3.4), `run_command.py` (P3.5), `list_command.py` (P3.6), `export_command.py` (P3.7), or `optimize_command.py` (P3.8), or their test files. Do not modify `src/cli/policies.py` (P3.8).

- **`cli.builders` is shared and evolvable.** Add new builder functions if needed; do not modify existing function signatures.

- **`cli.policies` is shared and frozen.** The concrete policies from P3.8 are reused without modification.

- **Minimum two strategies.** The compare command requires at least two `--strategy NAME` arguments. A comparison with fewer than two strategies is meaningless; validation occurs at the CLI argument level.

- **Withdrawal policy is shared.** All strategies in a single comparison use the same withdrawal policy, selected by name from the YAML file. This isolates the comparison variable to allocation strategy alone.

- **Orchestration lives in the CLI layer.** Following the established P3.5/P3.8 pattern (architectural debt D1 — see §Known Architectural Debt), the compare command orchestrates execution for each strategy directly. No application-layer comparison runner is created.

- **Evaluation results are pre-computed.** The compare command runs full simulations for each strategy and builds `EvaluationResult` sequences from the output. It does NOT implement the frozen `Evaluator` protocol (which requires a `get_evaluations(label)` method). Pre-computed sequences are simpler and sufficient for the v0.4 use case.

- **Persistence of individual strategies.** Each strategy's experiment definition, plan, and execution result are persisted to SQLite via existing `SQLiteRepository` methods. The comparison report itself is printed to stdout and NOT persisted — the underlying persisted data enables auditability and reproduction.

- **Exit codes:** 0 for success, 2 for validation error, 1 for execution error, 4 for database error, 130 for interruption.

## Architectural Analysis: StrategyComparator Integration

### The StrategyComparator Interface

The frozen v0.3 `StrategyComparator` at `src/engine/domain/optimizer/strategy_comparator.py` exposes this consumer-side API:

```python
class StrategyComparator:
    def __init__(self, metrics: Sequence[str], ranking_rule: RankingRule) -> None: ...

    def compare(
        self,
        strategy_map: Mapping[str, Union[Sequence[EvaluationResult], Evaluator]],
        group_by: GroupingDimension = "global",
    ) -> StrategyComparisonReport: ...
```

Where the supporting types (from `src/engine/domain/optimizer/types.py`) are:

```python
@dataclass(frozen=True)
class EvaluationResult:
    label: str
    metrics: Mapping[str, Decimal]
    provenance: Mapping[str, Sequence[str]]

@dataclass(frozen=True)
class RankingRule:
    primary_metric: str
    tie_breakers: Sequence[str]

GroupingDimension = Literal["parameter_config", "cohort", "global"]

@dataclass(frozen=True)
class StrategyComparisonReport:
    aggregated_metrics: Mapping[str, Mapping[str, Mapping[str, Decimal]]]
    ranking: Mapping[str, Sequence[str]]
    provenance: Mapping[str, Mapping[str, Sequence[str]]]
    diagnostics: Mapping[str, Mapping[str, str]]
```

### Integration Design

The compare command bridges the simulation execution layer to the StrategyComparator through these steps:

```
For each --strategy NAME:
    1. Select allocation policy from YAML by NAME
    2. Build ExperimentDefinition using shared policies + withdrawal policy
    3. Build ResearchPlan via cli.builders
    4. Execute plan (sequential or parallel)
    5. For each planned unit + simulation result pair:
       ─ Extract metrics: success (bool→Decimal), final_wealth, max_drawdown
       ─ Extract provenance: cohort_id, parameter_config canonical key
       ─ Build EvaluationResult(label=NAME, metrics={...}, provenance={...})
    6. Collect all EvaluationResults for this strategy into a list

Build strategy_map = {name: evaluations_list for each strategy}
Build RankingRule = RankingRule(primary_metric="success_rate",
                                tie_breakers=["final_wealth"])
Create comparator = StrategyComparator(metrics=["success_rate", "final_wealth", "max_drawdown"],
                                       ranking_rule=ranking_rule)
report = comparator.compare(strategy_map, group_by=group_by)
Print report
```

### Metric Computation

Each `SimulationResult` yields exactly one `EvaluationResult`. Metrics are derived from the simulation's `statistics` field:

| EvaluationResult Metric | Source | Type |
|------------------------|--------|------|
| `success_rate` | `1.0 if statistics.success else 0.0` | `Decimal` (1 or 0) |
| `final_wealth` | `statistics.final_wealth.amount` | `Decimal` |
| `max_drawdown` | `Decimal(str(statistics.max_drawdown))` | `Decimal` |

These are per-simulation-unit metrics. The StrategyComparator internally averages them across evaluations per label per group.

### Provenance Construction

Each `EvaluationResult` carries provenance enabling the comparator to group by cohort or parameter_config:

```python
provenance = {
    "cohort": [unit.cohort.id],           # single-element list: canonical cohort ID
    "parameter_config": [canonical_key],  # single-element list: canonical param config key
}
```

The canonical parameter_config key is the deterministic string representation of the configuration's sorted key-value pairs, e.g. `"equity_allocation=0.75"` or `"equity_allocation=0.75;glidepath_duration=10"`. This matches the expectation in the frozen comparator that `provenance["parameter_config"]` contains exactly one canonical identifier.

### Grouping Semantics

The `--group-by` argument maps directly to the `StrategyComparator.compare()` `group_by` parameter:

| `--group-by` | `group_by` value | Behavior |
|---|---|---|
| `global` (default) | `"global"` | All evaluation results aggregated under a single `"global"` group |
| `cohort` | `"cohort"` | Results grouped by cohort ID; one ranking per cohort |
| `parameter_config` | `"parameter_config"` | Results grouped by parameter configuration; one ranking per config |

## What Must Exist

### 1. `src/cli/commands/compare_command.py` — CompareCommand + helpers

Create three components within this file:

#### 1a. `_canonical_param_key(config: ParameterConfiguration) -> str`

Deterministic string key for a parameter configuration. Used for provenance grouping.

```python
def _canonical_param_key(config: ParameterConfiguration) -> str:
    """Return a deterministic canonical key for the parameter configuration.
    
    Example: "equity_allocation=0.75;glidepath_duration=10"
    """
    return ";".join(f"{name}={value}" for name, value in config.items())
```

#### 1b. `_extract_evaluation_results` — Simulation results → EvaluationResult list

```python
def _extract_evaluation_results(
    label: str,
    plan: ResearchPlan,
    result: ResearchExecutionResult,
) -> Sequence[EvaluationResult]:
    """Convert index-aligned plan units + simulation results into EvaluationResult objects.
    
    Each plan unit at index i maps to simulation result at index i.
    """
    evaluations: list[EvaluationResult] = []
    for i, (unit, sim_result) in enumerate(zip(plan.units, result.results)):
        success_val = Decimal("1") if sim_result.statistics.success else Decimal("0")
        evaluations.append(
            EvaluationResult(
                label=label,
                metrics={
                    "success_rate": success_val,
                    "final_wealth": sim_result.statistics.final_wealth.amount,
                    "max_drawdown": Decimal(str(sim_result.statistics.max_drawdown)),
                },
                provenance={
                    "cohort": [unit.cohort.id],
                    "parameter_config": [_canonical_param_key(unit.parameter_config)],
                },
            )
        )
    return evaluations
```

#### 1c. `CompareCommand` class

```python
class CompareCommand(BaseCommand):
    name = "compare"
    help_text = "Compare multiple allocation strategies side-by-side"

    def configure_parser(self, parser: argparse.ArgumentParser) -> None:
        parser.add_argument("study_file", type=str, help="Path to YAML experiment definition")
        parser.add_argument(
            "--strategy",
            type=str,
            action="append",
            required=True,
            dest="strategies",
            help="Name of allocation policy from YAML (repeatable, min 2)",
        )
        parser.add_argument(
            "--withdrawal-policy",
            type=str,
            default=None,
            help="Name of withdrawal policy from YAML (default: first withdrawal policy)",
        )
        parser.add_argument(
            "--group-by",
            choices=["global", "cohort", "parameter_config"],
            default="global",
            help="Grouping dimension for strategy comparison",
        )
        parser.add_argument(
            "--workers",
            type=int,
            default=1,
            help="Number of parallel workers",
        )
        parser.add_argument(
            "--initial-capital",
            type=str,
            default="1000000",
            help="Starting portfolio value in EUR",
        )

    def execute(self, context: ExecutionContext, args: argparse.Namespace) -> int:
        # 1. Validate at least 2 --strategy arguments
        # 2. Load and validate YAML
        # 3. Resolve dataset, build cohorts, build parameter configs
        # 4. Select withdrawal policy (--withdrawal-policy or first in YAML)
        # 5. Select allocation policies by --strategy names
        # 6. For each strategy:
        #    a. Build experiment definition
        #    b. Build research plan
        #    c. Record start_time = time.perf_counter()
        #    d. Execute plan:
        #       sequential_execute(plan) if workers == 1
        #       parallel_execute(plan, max_workers=workers) if workers > 1
        #    e. Record elapsed = time.perf_counter() - start_time
        #    f. Extract evaluation results
        #    g. Persist experiment, plan, and result with elapsed duration
        # 7. Build RankingRule and StrategyComparator
        # 8. Call comparator.compare(strategy_map, group_by)
        # 9. Print comparison report
        # 10. Exit 0
```

**Execution pattern per strategy.** Each strategy executes independently. When `--workers` is 1 (default), execution uses the single-worker path via `sequential_execute(plan)`. When `--workers` is greater than 1, execution uses the `ProcessPoolExecutor`-backed `parallel_execute(plan, max_workers=workers)`. This is the same pattern established by P3.8's `_SWREvaluator.evaluate()` (see `src/cli/commands/optimize_command.py:122-129`). The compare command does not distribute strategies across workers; each strategy is executed in its entirety before the next begins. The `--workers` flag controls intra-plan parallelism only, not inter-strategy parallelism.

**Execution duration.** Each strategy's execution duration is measured individually via `time.perf_counter()`, captured before and after the plan execution call. The measured `elapsed` (float seconds) is persisted with the execution result via `repo.save_execution_result()`. Durations are per-strategy so that execution time is independently attributable to each strategy in the persisted record.
```

### 3. Strategy selection from YAML

`_select_allocation_policy` is adapted from P3.8's `optimize_command.py` and duplicated (not imported) because it is a private helper specific to the command's YAML parsing context:

```python
def _select_allocation_policy(
    policies_data: list[dict[str, Any]], policy_name: str
) -> AllocationPolicy:
    for entry in policies_data:
        if entry.get("name") == policy_name:
            ratio = Decimal(str(entry.get("equity_ratio", "0.75")))
            return ConstantAllocationPolicy(equity_allocation=ratio)
    raise ValueError(f"Allocation policy '{policy_name}' not found in YAML")
```

Similarly, a `_select_withdrawal_policy` helper selects the withdrawal policy:

```python
def _select_withdrawal_policy(
    policies_data: list[dict[str, Any]], policy_name: str | None
) -> ConstantWithdrawalPolicy:
    """Select withdrawal policy by name, or return first if name is None."""
    target = policy_name
    for entry in policies_data:
        if target is None or entry.get("name") == target:
            rate = Decimal(str(entry.get("withdrawal_rate", "0.04")))
            return ConstantWithdrawalPolicy(withdrawal_rate=rate)
    raise ValueError(
        f"Withdrawal policy '{policy_name}' not found in YAML"
        if policy_name
        else "No withdrawal policies defined in YAML"
    )
```

**Validation rules:**
- If `--strategy NAME` does not match any YAML allocation policy name, exit code 2 with descriptive error.
- If `--withdrawal-policy NAME` does not match any YAML withdrawal policy name, exit code 2.
- If `--initial-capital` is non-numeric, exit code 2.
- If fewer than 2 `--strategy` values provided, exit code 2 with "At least two strategies are required for comparison".

### 7. Persistence

The compare command persists each strategy's experiment definition and execution result using existing `SQLiteRepository` methods. The comparison report itself is not persisted.

**Timing.** Each strategy has an individual execution duration (`elapsed`), captured via `time.perf_counter()` immediately before and after the plan execution call (see §1c step 6e). This per-strategy duration is the value passed to `save_execution_result()`.

```python
import time

for strategy_name, (experiment_def, plan, execution_result) in strategy_results.items():
    try:
        elapsed = ...  # captured per-strategy in step 6c-6e of execute()
        db_path = str(Path("~/.sim-retire/studies.db").expanduser())
        repo = SQLiteRepository(db_path)
        persistence_context = create_persistence_context(context.data_dir)
        identity = ExperimentIdentity(
            name=f"{study_name} - {strategy_name}",
            revision="1.0",
        )
        experiment_id = repo.save_experiment(identity, experiment_def, persistence_context)
        plan_id = repo.save_plan(plan, experiment_id, persistence_context)
        repo.save_execution_result(plan_id, execution_result, persistence_context, elapsed)
    except Exception as exc:
        print(f"WARNING: Persistence failed for strategy '{strategy_name}': {exc}", file=sys.stderr)
```

The `elapsed` variable is populated per-strategy during the execution loop (step 6), not computed after all strategies complete. Each persisted execution result carries its own independent duration, ensuring accurate timing attribution.

Each strategy's persisted data is individually retrievable via `sim-retire list` and `sim-retire export`. The comparison can be reproduced by re-running the same strategies.

### 8. Error handling

| Condition | Exit Code | Behavior |
|-----------|-----------|----------|
| File not found | 2 | Print error, return VALIDATION_ERROR |
| Invalid YAML | 2 | Print parse error with line number |
| Fewer than 2 `--strategy` values | 2 | Print "At least two strategies required" |
| Strategy name not found in YAML | 2 | Print "Allocation policy 'X' not found" |
| Withdrawal policy not found | 2 | Print "Withdrawal policy 'X' not found" |
| No withdrawal policies in YAML | 2 | Print error |
| `--initial-capital` non-numeric | 2 | Print descriptive validation error |
| Cohort generation failure | 2 | Print error |
| Parameter config build failure | 2 | Print error |
| Execution failure for a strategy | 1 | Print error with strategy name, continue other strategies if possible |
| All strategies fail | 1 | Print "All strategies failed", return ERROR |
| Database unreachable | 4 | Print error, return DATABASE_ERROR |
| KeyboardInterrupt | 130 | Print interruption message |
| Successful comparison | 0 | Print comparison report |

**Partial failure handling:** If one strategy's execution fails but others succeed, the failing strategy is skipped with an error message, and the comparison proceeds with the remaining strategies. If `len(remaining_strategies) < 2`, the command exits with code 1 and "Fewer than 2 strategies completed".

## Acceptance Criteria

1. `sim-retire compare valid_study.yaml --strategy "75/25" --strategy "60/40"` prints a ranked comparison and exits 0.
2. `sim-retire compare valid_study.yaml --strategy "75/25" --strategy "60/40" --strategy "50/50"` compares 3 strategies and exits 0.
3. `sim-retire compare valid_study.yaml --strategy "75/25" --strategy "60/40" --group-by cohort` shows per-cohort rankings.
4. `sim-retire compare valid_study.yaml --strategy "75/25" --strategy "60/40" --group-by parameter_config` shows per-parameter-config rankings.
5. `sim-retire compare valid_study.yaml --strategy "75/25" --strategy "60/40" --workers 4` uses parallel execution.

## Architecture Review: Key Decisions

### Decision 1: Pre-computed EvaluationResult sequences (not Evaluator protocol)

The thawed `Evaluator` protocol in `engine.domain.optimizer.types` requires `get_evaluations(label: str) -> Sequence[EvaluationResult]`. The compare command could implement this protocol by wrapping the execution pipeline in a class that accepts a label and returns results. However, this adds indirection without benefit:

- **Pre-computed approach:** The compare command executes all strategies upfront, collecting results per strategy. This is simpler and matches the batch-execution pattern well.
- **Evaluator approach:** Lazy evaluation (only compute results when the comparator iterates). This would require the comparator to drive the iteration order, which adds complexity.

**Resolution:** Use pre-computed `Sequence[EvaluationResult]` for each strategy. The `compare()` method accepts `Union[Sequence[EvaluationResult], Evaluator]`, so both approaches are valid. Pre-computed is cleaner for the CLI use case.

### Decision 2: `_canonical_param_key` in CLI, not shared module

The parameter configuration canonical key function is small (3 lines) and only used by the compare command. It is kept private to `compare_command.py` rather than added to `cli.builders`. If a second consumer emerges (P3.10 or Phase 4), it can be promoted.

### Decision 3: Duplicated `_select_allocation_policy` (not imported from optimize)

The `_select_allocation_policy` function in `optimize_command.py` is a private helper (`_` prefix). The compare command duplicates the same logic rather than importing a private function from a frozen command. This follows the P3.4→P3.5 pattern where policy construction was intentionally not shared.

**Rationale:** The optimize command's private helper could change shape if optimize evolves. The compare command's needs are slightly different (it returns an `AllocationPolicy`, whereas optimize's helper also handles warning emission). Duplication of 6 lines of logic is acceptable and maintains proper encapsulation boundaries.

### Decision 4: Withdrawal policy from YAML (not hardcoded)

Unlike P3.8 which hardcodes the withdrawal rate via `--target-success-rate` and binary search, P3.9 uses a fixed withdrawal policy selected from the YAML file. This is because:
- The compare command compares allocation strategies at a fixed withdrawal rate (not optimized)
- The withdrawal rate should come from the study definition, not a CLI argument
- Users create withdrawal policy entries in the YAML with specific rates

The `--withdrawal-policy NAME` argument selects which policy to use, defaulting to the first.

### Decision 5: Partial failure handling

If one strategy's execution fails, the compare command continues with the remaining strategies. This is a deliberate design choice:
- A strategy may fail due to dataset, policy, or execution issues independent of other strategies
- Partial results are more useful than a complete failure
- The user is informed about the failure via stderr
- If fewer than 2 strategies remain, the command exits with code 1

This mirrors the P3.5/P3.8 execution error handling where individual failures are reported but do not cascade.

### Decision 6: Comparison report not persisted

The `StrategyComparisonReport` is printed to stdout but not stored in SQLite. Rationale:
- The underlying execution results for each strategy are persisted (experiment, plan, execution result)
- The comparison can be reproduced by re-running the same strategies
- Persisting the report would require new database schema (comparison_results table, comparison_to_strategy mapping)
- v0.4 schema is frozen; schema changes require an ADR

If audit trail requirements demand persisted comparison metadata in the future, a dedicated `comparison_results` table can be added via a new ADR.

### Decision 7: Metrics selection

Three metrics are used: `success_rate` (primary), `final_wealth` (tie-breaker), `max_drawdown` (informational). These are:
- Directly derivable from the existing `SimulationStatistics` output of every executed simulation
- Meaningful for SWR strategy comparison
- Consistent with the ERN study methodology

Additional metrics (CAGR, ulcer index, etc.) could be added by extending `_extract_evaluation_results` with computations from the simulation timeline. This is deferred to post-v0.4.

## Known Architectural Debt / Risks

The following items are **accepted** for P3.9. They do not block implementation but are documented to inform future architecture work.

| ID | Item | Classification | Impact |
|----|------|---------------|--------|
| D1 | **Orchestration lives in the CLI layer.** The compare command directly orchestrates strategy execution, plan building, and result extraction. No application-layer `comparison_runner` exists. This extends the same pattern from P3.5/P3.8 (D1 from P3.8). | Acceptable debt, post-v0.4 refactoring target | Duplicates P3.5/P3.8 orchestration pattern; increases CLI-layer coupling to execution infrastructure |
| D2 | **Pre-computed evaluation results.** The compare command passes pre-computed `Sequence[EvaluationResult]` to the comparator rather than implementing the `Evaluator` protocol. This is simpler but means all strategies must be fully executed before comparison begins. | Acceptable design choice | No lazy evaluation; memory grows linearly with N strategies × plan units. Acceptable for v0.4 scale |
| D3 | **Metrics limited to `SimulationStatistics`.** Only `success`, `final_wealth`, and `max_drawdown` are extracted. The simulation timeline (`monthly_results`) contains rich per-month data (withdrawal amounts, portfolio values, drawdown paths) that could produce more nuanced metrics (e.g., mean monthly withdrawal, ulcer index, path-dependent risk measures). | Acceptable limitation | Trivially extendable in `_extract_evaluation_results` by computing aggregate metrics from `sim_result.timeline.monthly_results` |
| D4 | **Comparison report not persisted.** The `StrategyComparisonReport` is printed and lost on process exit. The underlying per-strategy execution results are persisted, but the ranked comparison output is not stored. | Acceptable, pre-existing pattern (P3.8 D3 equivalent) | Reproduction requires re-running the comparison. Schema addition would require ADR |
| D5 | **YAML policy selection duplicated from P3.8.** The `_select_allocation_policy` helper replicates the logic from `optimize_command.py`. This is intentional (private helper, frozen command boundary) but creates a maintenance burden if the YAML policy schema changes. | Acceptable duplication | 6 lines of logic. Revisit if YAML schema evolves |
| D6 | **No validation of strategy independence.** The compare command treats each `--strategy` as an independent allocation policy. If two `--strategy` values select the same YAML policy, the comparison is meaningless (identical inputs → identical outputs → equal metrics). | Acceptable limitation | User responsibility. Could add a duplicate-name warning in a future package |
