## Executive Summary

P3.10 implements configuration management for the FIRE Backtesting Framework CLI. It provides:

- Global `--config FILE` option for CLI configuration file loading
- `sim-retire config` command for inspection, validation, and modification of configuration
- Configuration model, precedence rules, and validation
- Documentation completion and handoff preparation
- Phase 3 integration validation preparation

This package closes the CLI configuration aspect of Phase 3. It integrates with the existing frozen infrastructure and CLI layers while maintaining clean architecture boundaries (CLI owns configuration, infrastructure persists simulation data only).

---

## Architectural Constraints

- **No frozen domain changes.** All code lives in the CLI layer (`src/cli/commands/`) or infrastructure persistence layer (`src/infrastructure/persistence/`). No `engine.*`, `research.*`, or `research.optimization.*` files are modified — only their frozen public APIs are consumed.

- **Configuration is CLI layer responsibility.** All configuration logic, parsing, validation, and precedence rules reside in the CLI (`src/cli/commands/config_command.py`). Infrastructure provides only persistence storage through SQLite via existing `SQLiteRepository` methods.

- **No frozen command changes.** Do not modify `validate_command.py`, `run_command.py`, `list_command.py`, `export_command.py`, `optimize_command.py`, or `compare_command.py` unless configuration is explicitly required by their frozen implementations.

- **`cli.builders` is shared and evolvable.** Add new builder functions if needed; do not modify existing function signatures.

- **`cli.main.py` is frozen.** The CLI entry point and parser configuration (`_build_parser()`) are frozen. Configuration file loading must integrate through this interface.

- **Minimum YAML-based configuration.** Configuration uses YAML files following `~/.sim-retire/config.yaml` format. All configuration values must be validated and serialized as YAML.

**Model:** Configuration parsing, validation, and management reside in `src/cli/commands/config_command.py`. The CLI layer builds configuration objects for use by CLI commands.

**Rationale:**
- Configuration is user-facing input processing → Presentation layer responsibility
- Prevents domain logic dependencies on configuration
- Enables multiple output formats (YAML, CLI)
- Maintains clean separation: CLI → Application → Domain

### Decision 2: YAML is the Single Source of Truth

**Model:** All configuration management operates exclusively on YAML files. No persistent storage in Infrastructure layer.

**Implementation:**

```python
# Configuration loaded from YAML file via builders
# src/cli/builders.py
def load_config_file(path: Path) -> dict[str, Any]:
    """Load and validate YAML configuration file."""
    if not path.exists():
        raise FileNotFoundError(str(path))
    raw = path.read_text(encoding="utf-8")
    data = yaml.safe_load(raw)
    if not isinstance(data, dict):
        msg = "Configuration YAML root must be a mapping"
        raise yaml.YAMLError(msg)
    return data
```

```yaml
# ~/.sim-retire/config.yaml
---
output:
  default_format: csv
  default_directory: ./results/
  
execution:
  default_workers: 4
  max_workers: 16
  timeout_seconds: 3600
  
logging:
  level: INFO  # DEBUG, INFO, WARNING, ERROR
  file: ~/.sim-retire/sim-retire.log
```

**Rationale:**
- YAML alone serves as user configuration source (CLI Interface Spec §2.2)
- Configuration is input data, not business logic → CLI layer responsibility
- No persistence avoids Infrastructure layer boundary violations
- Simple file I/O, easier to reason about and test
- Consistent with P3.10 scope limiting Infrastructure changes to Phase 2 definition

### Decision 3: Three-Level Configuration Precedence

**Model:** CLI follows the v0.4 architecture-defined configuration precedence hierarchy:

1. **User Configuration** (CLI arguments / config file)
2. **Study Configuration** (ExperimentDefinition)
3. **System Configuration** (application defaults)

**Implementation:**

```yaml
# ~/.sim-retire/config.yaml
---
output:
  default_format: csv
  default_directory: ./results/
  
execution:
  default_workers: 4
  max_workers: 16
  timeout_seconds: 3600
```

**Rationale:**
- Implements Three-Level Configuration from v0.4 Milestone Architecture (§3.4)
- Aligns with existing CLI Interface Specification (§2.2-2.3)
- Maintains separation of concerns across configuration layers
- Provides clear, predictable hierarchy for configuration management

## Acceptance Criteria

1. **CLI Configuration Integration:** `sim-retire run --config file.yaml studies/part19.yaml` loads YAML configuration and applies precedence rules correctly.

2. **Configuration Command Operations:**
   - `sim-retire config set key value` sets configuration in YAML
   - `sim-retire config get key` retrieves configuration from YAML
   - `sim-retire config list` lists all YAML configuration values
   - `sim-retire config validate` validates YAML configuration

3. **YAML Persistence:** Configuration is persisted to YAML file and can be retrieved for later use.

4. **Precedence Rules:** Configuration precedence is correctly implemented: CLI args > config file > defaults.

5. **Error Handling:** Invalid configuration produces ExitCode.CONFIGURATION_ERROR (3) with descriptive error messages.

6. **Help Text:** `sim-retire config --help` and `sim-retire config set --help` provide comprehensive usage.

7. **Type Checking:** `mypy src/cli/ --strict` reports 0 errors.

8. **Regression Testing:** All existing tests continue passing.

9. **Documentation:** All configuration behavior documented in CLI Interface Specification.

10. **Integration:** Configuration integrates with existing study execution pipeline (validate, run, list, export, optimize, compare commands).
